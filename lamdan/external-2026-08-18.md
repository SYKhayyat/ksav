# Ksav — external audit, 2026-08-18

Audited against `d546811` plus the working tree. Scope: `ksav/engine` (Rust),
`ksav/app/src` (TypeScript), `ksav/app/src-tauri` (Rust), the HTTP contract, and
the running product.

**This file is deliberately untracked**, for the same reason
`AUDIT-perf-and-blocking.md` says it is: `app/test/documentation.test.mjs`
partitions every *tracked* `.md` into living pages and log records and
default-denies anything else. If any of this should be kept, it belongs in
`decisions/2026-08-18-<slug>.md` with the partition list updated in the same
commit.

## Method, and what that means for confidence

Primary method was reading. The engine's request path, service registry, server,
git driver, asset cache, include expansion and post/loopback were read in full;
on the client, `main.ts` was read through the editor, pane, document, file,
scroll and boot regions, and `api.ts`, `store.ts`, `save.ts`, `compile.ts`,
`docs.ts`, `files.ts`, `watch.ts`, `preview.ts`, `opendocs.ts`, `paneplaces.ts`,
`parts.ts`, `runtime.ts`, `crash.ts`, `share.ts`, `settings.ts`,
`ksav-lang.ts` (the HTML-producing half) were read in full.

A second pass then went through the notes and apparatus region — `notes.ts`,
`note-commands.ts`, `insert.ts`, `apparatus.ts`, `apparatus-lint.ts`, and the
note context menu in `main.ts` — which the repository's own history flags as its
weakest area. §6 is what that pass found; it is the strongest section in this
report.

Reading was then checked against the running product: `npm test` (96 files,
6,596 assertions, **green** — every finding below is in territory the suite does
not cover), the release binary under `ksav serve`, the app driven in a headless
browser, and seven purpose-written probes.

Each finding is tagged:

* **CONFIRMED** — reproduced by executing something. The evidence is quoted.
* **CODE** — established by reading, with the mechanism named. I did not build
  a reproduction, usually because the trigger needs Girsa, a Tauri build, or a
  filesystem state I did not want to manufacture.

A note on the shape of this codebase, because it changes what an audit is worth
here: almost every module carries a long comment describing a defect it already
fixed. That is unusually good, and it has a specific consequence — **the
interesting bugs left are inside the fixes**. Three of the findings below
(§1.1, §2.1, §3.1) are defects in the machinery that
`AUDIT-perf-and-blocking.md` introduced earlier today. That audit's items are
genuinely landed; these are what landed with them.

### Coverage I did not reach

Stated plainly, because a list of findings implies a boundary and the boundary
should not have to be inferred. Not read, or read only in outline:
`deferred.ts`, `structure.ts`, `styles.ts`, `panelviews.ts`, `table.ts`,
`i18n.ts`, `channels.ts`, `docx.ts`, `org.ts`, `interchange.ts`, the styles-panel
region of `main.ts` (roughly lines 9200–11400), the Typst prelude `ksav.typ`,
the Emacs client, and the engine's `spell/`, `jump.rs`, `pagelines.rs`,
`notemarks.rs`, `diagnostics.rs`, `sefarim.rs`. `cargo test` was not run (a full
run needs tens of gigabytes and this machine is at 91%; see
`ksav-cargo-disk-corruption`). Nothing below depends on those areas.

The one I would go back for first is **`styles.ts` and the styles panel**. §6
shows the Hebrew-only assumption is not one slip but a pattern that survives
wherever a command name is written as a literal rather than derived from the
family tables, and the styles panel writes command names in bulk.

One hypothesis I formed and **disproved**, recorded because a report that only
lists confirmed hits is not showing its work: I expected the note context menu
to leak, since it is appended straight to `document.body` and nothing removes it
by name. It does not — see §6.4 for what is actually true, which is a weaker
finding than the one I went looking for.

# §1 — Security

The threat model this engine is actually deployed under is stated in
`server.rs`: *"the comment further down about this server binding to loopback
and holding no secrets was written before `/inbox` existed. It is also not quite
true any more: `ksav serve [addr]` takes any bind address."* The findings below
are what that sentence has not yet been followed through to.

## 1.1 — `/git` is fully reachable by any caller that sends no `Origin` — **CONFIRMED**

`engine/src/server.rs::origin_allowed`:

```rust
fn origin_allowed(request: &tiny_http::Request, addr: &str) -> bool {
    origin_of(request).is_none_or(|o| allowed_origin(&o, addr))
}
```

An absent `Origin` is allowed, deliberately, so `curl` and the Tauri shell work.
That is a reasonable rule for the services the comment was written about. It is
not a reasonable rule for `git`, which arrived later and which the doc comment
above `git_request` describes as *"seventeen operations"* including `commit`,
`push`, `restore`, `revert`, `remote-add` and `merge`.

`Asked.path` is an arbitrary absolute path, so the caller chooses the
repository. `locate` derives the repo from it; nothing constrains it to a
document Ksav has open, or to a document at all.

Reproduced against the release binary:

```
$ curl -s -X POST http://127.0.0.1:7878/git -H 'Content-Type: application/json' \
    -d '{"op":"status","path":"C:/Users/Administrator/Videos/Ksav/ksav/README.md"}'
{"ahead":0,"behind":0,"branch":"main","detached":false,
 "files":[{"kind":"untracked","path":"ksav/engine/-o/",...}],
 "git":"2.54.0.windows.1","head":"63da5edd...","root":"C:/Users/Administrator/Videos/Ksav",...}

$ curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:7878/git \
    -H 'Origin: https://evil.example' ... 
403
```

The cross-origin half is correctly closed. What is open is everything that is
not a browser: any process on the machine (which on a shared or managed box is
not the same set as "the writer"), and — because `serve` takes any bind address
and there is no authentication anywhere — any host on the network the moment
somebody runs `ksav serve 0.0.0.0:7878` to read their sefer from a tablet. That
is not a hypothetical use; it is the obvious reason to type an address at all,
and nothing warns against it.

What it buys an attacker: read any file at any revision in any repository on the
machine (`op: "show"`), write to the working tree (`restore`), create commits,
`push` to a remote of their choosing, and — see §1.3 — run a command.

**Fix.** The desk (`post.rs`) already has the right shape: a token in a file only
the two installed applications can read. `/git` and the five other `Reach::Native`
services should require the same token, or `serve` should refuse a non-loopback
bind address unless a token is configured. `Reach` is already the column that
distinguishes them, so this is a check in `handle()` keyed on `svc.reach`, not a
per-service change.

## 1.2 — The engine's asset cache trusts a hash it never verifies — **CONFIRMED**

`engine/src/assets.rs::read_one_cached` stores bytes under whatever string the
caller put in `hash`, and later resolves a hash-only entry from that map. It
never hashes the bytes it was given.

```
1) send bytes under an arbitrary hash  -> missing: []
2) hash only, DIFFERENT name           -> missing: []       ← resolved from the cache
3) hash only, never seeded             -> missing: ["A-HASH-NOBODY-EVER-SENT"]
```

Row 2 is the finding: a request that carried no bytes, under a name the engine
had never seen, was silently handed the bytes some earlier request associated
with that key. The cache is process-wide and shared across every document and
every window talking to one `ksav serve`.

Two consequences, and the second is the one that will actually bite:

* **Poisoning.** Combined with §1.1 (no `Origin` is allowed), any local process
  can seed hash `H` with bytes of its choosing before the writer's client asks
  for `H`. The writer's sefer then prints somebody else's image.
* **Collisions are not scoped the way the client thinks they are.**
  `app/src/docs.ts::assetHash` is two 32-bit FNV-1a passes plus the length, and
  its comment reasons about the risk correctly for the wrong set: *"vanishingly
  unlikely for the handful of images a document carries."* The collision domain
  is not one document's handful. It is every asset the engine has seen since the
  process started, across every document in the library, bounded only by
  `CACHE_CAP_BYTES = 256 MB`. A 64-bit hash over that set is still fine in
  practice, but the argument written down does not establish it, and the
  argument is the thing that will be re-read when somebody shrinks the hash.

**Fix.** Verify on insert: hash the decoded bytes with the engine's own function
and refuse (or re-key) a mismatch. That closes the poisoning outright and makes
the collision argument true as stated, because the key would then be the
engine's hash rather than the client's claim.

## 1.3 — `remote-add` accepts a transport that executes a command — CODE

`engine/src/git.rs::plain` refuses a leading `-`, an embedded NUL and a newline,
and its doc comment is explicit that it is *"deliberately not a character
whitelist"* because Hebrew paths must survive. That is right for branches and
paths. It is not sufficient for a **URL**:

```rust
fn remote_add(place: &Place, asked: &Asked) -> String {
    ...
    if let Err(e) = plain(url, "remote address") { return e; }
    match git_run(&place.dir, &["remote", "add", name, url]) { ... }
```

`ext::sh -c 'whoami'` does not begin with a dash, contains no NUL and no
newline, so `plain` passes it. git's `ext::` transport runs the rest of the
string as a command on the next `fetch`, `pull` or `push` — all three of which
`network()` offers as operations on the same service. `protocol.ext.allow` is
`user` by default, which permits it for a remote the user configured, and from
git's point of view this remote *was* configured by the user.

Reachable through §1.1 by anything that can POST. Also reachable through the
`.ksav` route in a weaker form: a document is a file somebody emails, and the
remote-add field is a text box in the drawer.

**Fix.** For the URL specifically, require a scheme from an allow-list
(`https`, `ssh`, `git`, `file`, plus bare `user@host:path`), or set
`-c protocol.ext.allow=never` in `git_run`'s standing `-c` list. The second is
one line and costs nothing anybody wants.

# §2 — Races

## 2.1 — The wasm two-lane queue disables itself permanently after any worker timeout — **CONFIRMED**

`app/src/api.ts::WasmBackend`. `call()` holds a background job while any
foreground job is outstanding, and releases the lane when the counter reaches
zero:

```ts
if (!background) this.foregroundPending++;
try { return await this.post(name, input, timeoutMs); }
finally { if (!background && --this.foregroundPending === 0) this.drainBackground(); }
```

`failAll()` — reached by the compile timeout and by `w.onerror` — resets the
same counter to zero while those `finally` blocks are still pending:

```ts
this.foregroundPending = 0;
this.drainBackground();
```

Each outstanding foreground call then decrements from zero. The counter goes
negative and never returns: `foregroundPending > 0` is false forever, so nothing
is ever held; `--this.foregroundPending === 0` is false forever, so the lane is
never drained from the foreground side either.

Probe against the built module (`.tmp-test/api.mjs`, worker stubbed to never
answer):

```
start foregroundPending = 0
in flight foregroundPending = 2
[ 'rejected:timeout', 'rejected:timeout' ]
after failAll foregroundPending = -2
background job started while a foreground compile is outstanding? true
foregroundPending during = -1
```

The last two lines are the defect stated as behaviour: after one worker death,
the browser build is back to plain FIFO, which is exactly what
`AUDIT-perf-and-blocking.md` §B1 was written to fix — *"a background layout or
the 1 Hz inbox poll in front of the compile the writer was waiting for"*. It
comes back silently, and it comes back at the worst moment: a worker dies
because a document ran away, which is when the next compile matters most.

**Fix.** `failAll` should not zero the counter that the unwinding `finally`
blocks still own. Either drop the reset and let the `finally` blocks drain
naturally, or clamp: `this.foregroundPending = Math.max(0, this.foregroundPending)`
in the `finally`. A test that asserts the counter is non-negative after a
timeout is the cheap fence.

## 2.2 — `openDoc` is re-entrant across its awaits — CODE

`app/src/main.ts::openDoc` opens with

```ts
const next = await docs.getDoc(id);
if (!next) return;
if (opendocs.focusedId() === id && runtime.currentDoc?.id === id) return;
await flushSaves();
runtime.setSwitching(true);
```

and closes, after `setSwitching(false)`, with `await refreshBaseline()` followed
by six more mutations of global state (`forgetGit`, `updateTitleBar`,
`rerenderChrome`, `refreshPaneHeads`, `showPagesFor`, `restorePreviewPlaces`).

The only guard is an early return for *the same* id. Two switches to *different*
documents — the switcher panel is a list of buttons, and `Mod-1`-style tab keys
are bound — can interleave at either `await`. The observable results are:
`refreshBaseline()` dispatching document A's snapshot baseline into a view now
holding B; `rememberPages(leaving)` filing B's on-screen pages under A's id; and
`retargetPanes(leaving, id)` relabelling panes for a document that is no longer
arriving.

`setSwitching` looks like the guard and is not one — it is a flag the change
listener reads, it is cleared in the middle of the function, and it does not
prevent a second entry.

Note the file already knows this shape is needed: the binding recall five lines
later does exactly the right thing —

```ts
void files.recallBinding(next.id).then((b) => {
  if (runtime.currentDoc?.id !== next.id) return;   // a newer switch has won
```

— and the rest of the function does not.

**Fix.** Take a ticket, the way `runCompile` and `runSpellCheck` do
(`const mine = ++switchGeneration`), and return after each await when
`mine !== switchGeneration`. Or serialise: hold a `switchPending` promise the
way `save.ts` holds `savePending`.

## 2.3 — The Girsa poll grows a timer chain per focus that lands mid-poll — **CONFIRMED (simulation)**

`app/src/main.ts::installBackgroundTimers`. There is one `pollTimer` variable and
`arm()` overwrites it, so `wake()` can only cancel the *most recent* timer:

```ts
const arm  = (ms) => { pollTimer = window.setTimeout(runPoll, ms); };
const wake = () => { pollDelay = GIRSA_POLL_MS; clearTimeout(pollTimer); arm(0); };
window.addEventListener("focus", wake);
```

Once `runPoll` has fired it is no longer cancellable, and it ends with its own
`arm(pollDelay)`. So a `wake()` that arrives while a poll is awaiting the inbox
produces a second chain, and the two are thereafter independent. Faithful
extraction of the loop, six tab-returns each landing during an in-flight poll:

```
live timer chains after 6 tab-returns: 7   polls run: 15
```

Seven chains where the design has one. It never recovers — nothing in the loop
can observe or collapse a duplicate.

Live against the running product I could **not** trigger it: on `ksav serve` over
loopback a poll completes in about a millisecond, so `wake` essentially never
lands inside one, and the poll rate measured correctly (0 polls in 20 s at the
30 s backoff, 1 poll after a wake). The trigger is a slow inbox — the desktop
build, where the service goes through `spawn_blocking` behind a compile; or
Girsa itself being slow. So: real, unbounded, and conditional.

**Fix.** Guard the chain rather than the timer: an epoch counter incremented by
`wake()` and checked in `runPoll` before it re-arms, so a superseded chain
retires instead of re-arming.

## 2.4 — `TauriBackend.compile` leaves an unhandled rejection behind, and the crash panel catches it — CODE

```ts
const run = this.cache.compile(...);
const deadline = new Promise<CompileResult>((resolve) => {
  timer = setTimeout(() => resolve(errorResult(COMPILE_TIMEOUT_MESSAGE)), COMPILE_TIMEOUT_MS);
});
return await Promise.race([run, deadline]);
```

When the deadline wins, `run` is still outstanding and nothing is attached to it.
If it later rejects — a Tauri `invoke` rejection, a JSON parse failure on a
truncated answer — that is an unhandled promise rejection.

`crash.install` registers `window.addEventListener("unhandledrejection", …)` and
its handler puts the **full-screen crash panel** over the application. So on the
desktop build, a compile that overruns twenty seconds and then fails can present
the writer with "Ksav has crashed", over an application that has not crashed, in
the middle of a document that is fine.

**Fix.** `run.catch(() => {})` at the point the race is set up. One line, and it
also removes the console noise.

## 2.5 — The spell menu acts on offsets captured before an await — CODE

`app/src/main.ts::openSpellMenu` captures the misspelling `m`, then awaits
`backend.suggest(...)`, then builds a `replace` closure that dispatches
`{ from: m.start, to: m.start + m.len }`.

The only staleness check is `if (!box.isConnected) return;` — which asks whether
the menu is still on screen, not whether the document still says what `m`
described. The menu is not modal: the editor keeps focus behaviour, the document
keeps taking edits from a mirrored pane, from `takeArrivals`, from a background
`linkify`. Accepting a suggestion after any of those replaces the wrong span.

The same closure is reached from the keyboard route (`spellSuggest`), which is
the route a fast writer uses.

**Fix.** The pattern is already in the file — the paste handler does it
correctly:

```ts
const here = docTextOf(v.state.doc).slice(from, from + plain.length);
if (here !== plain) return;
```

`replace` should make the same check against `m.word` before dispatching.

# §3 — Inefficiencies

## 3.1 — The incremental spell check still scans the whole document, every beat — **CONFIRMED (measured)**

`runSpellCheck` was made incremental (dirty region, paragraph widening, splice
back). The payload it *sends* is now one paragraph. What it *computes* is still
the whole sefer:

```ts
const realText = docTextOf(doc);
const checkable = spell.checkableText(realText, { comments: !!settings.spellcheckComments });
...
const payload = full ? checkable : checkable.slice(region.from, region.to);
```

`checkableText` runs `proseRegions` over the entire document, allocates an array
with one entry per UTF-16 code unit, fills it, and joins it — then the result is
sliced to one paragraph. Measured on the built module:

```
64 KB document:  checkableText = 3.2 ms per call
200 KB document: checkableText = 8.0 ms per call
```

On the main thread, on a 700 ms timer, while the writer is typing. Half a frame
budget on a 200 KB sefer, to produce a paragraph.

This is the one finding here that `AUDIT-perf-and-blocking.md` §A6 partially
addressed — it fixed the transfer and the engine's work, and left the client's.

**Fix.** Widen the dirty region to paragraph boundaries first (that already
happens), then run `checkableText` over `realText.slice(region.from, region.to)`.
The function is offset-preserving within whatever it is given, so the splice
arithmetic is unchanged.

## 3.2 — `includedParts` reads the whole library and memoises it forever — CODE

`app/src/compile.ts`:

```ts
if (!parts.referenced(body).length) return [];
const byTitle = new Map<string, string>();
for (const entry of docs.library()) {     // ← every document in the library
  ...
  const doc = await docs.getDoc(entry.id);
  partMemo.set(entry.id, { updated: entry.updated, body: doc.body });
```

A document that includes one chapter causes every document in the library to be
read out of IndexedDB and held in `partMemo` — bodies and all — for the life of
the tab. A forty-document library of 200 KB seforim is eight megabytes retained
to resolve one `#כלול`, and forty IndexedDB round trips on the first compile
after a name is typed.

The comment for `parts.ts` states the opposite intent: *"to do it without
sending the whole library on every keystroke — a writer with forty documents open
would otherwise pay for all forty on every pause in typing."* The sending was
fixed; the reading was not.

`parts.collect` already takes a `lookup(name)` callback, so the resolution is
demand-driven by construction — it is only the pre-population that is eager.

**Fix.** Resolve names on demand: walk `parts.referenced` transitively, reading
only the titles actually asked for. `partMemo` should also be bounded, or keyed
by title with the body dropped once the request is built.

## 3.3 — The engine copies every cached asset twice per compile — CODE

`engine/src/assets.rs::read_one_cached`:

```rust
if let Some(h) = &hash {
    cache().lock().ok()?.put(h.clone(), Arc::new(bytes.clone()));   // ← full copy
}
return Some(Asset { name, bytes });
...
Some(bytes) => Some(Asset { name, bytes: (*bytes).clone() }),      // ← full copy, every compile
```

The `Arc` is doing no work: `Assets.files` holds `Vec<Asset>` with an owned
`Vec<u8>`, so a cache *hit* clones the whole image out of the `Arc` on **every
compile** — which is every pause in typing. An 8 MB attachment (the ceiling
`attachAsset` enforces) is an 8 MB memcpy per keystroke-driven compile, plus
another 8 MB on the request that first carried it.

The cache's own header states what it was for: *"an 8 MB image is ~11 MB of
base64, and the editor re-sent the whole asset array on every pause in typing …
plus a base64 decode of it here each time."* It removed the transfer and the
decode and kept the copy.

**Fix.** `Asset.bytes: Arc<Vec<u8>>`. `engine_for` hands the bytes to Typst's
file resolver, which can take a slice; nothing in the compile path needs
ownership. On insert, build the `Arc` once and clone the handle rather than the
buffer.

## 3.4 — `include::expand` rebuilds the body and a per-line map on every request — CODE

`read_document` calls `include::expand(body, &parts)` unconditionally, and
`expand_into` pushes one `Origin` and one line copy per line of the input. The
doc comment says *"a request with no `parts` expands to itself, at no cost."*

It is not free. For a 200 KB document with no `#כלול` at all — the common case —
every compile, jump, reveal and assemble allocates a fresh 200 KB `String` and a
`Vec<Origin>` of roughly five thousand entries, then throws both away.

**Fix.** Short-circuit: if `referenced(main).is_empty()`, return an `Expanded`
that borrows or moves the body with a lazily-built map. The `origins` vector is
only read by `relabel`, `pagelines::relabel` and `notemarks::keep_main`, all of
which can answer trivially when there was no expansion.

## 3.5 — `library()` re-sorts on every call, and is called inside loops — CODE

`docs.ts::library()` maps, sorts and maps again on every invocation. Call sites
that do it per item:

* `openSwitcher` — `docs.library().find(...)` once per open document.
* `buildTabStrip` and `openPaneMenu` — `titleOf` closes over `docs.library()`
  and is called once per tab.
* `boot`'s `onGoToPart` handler, `docBoundTo`, `movePaneToTab`.

O(n log n) per lookup where O(1) is available. Small today; it is the shape that
gets noticed at two hundred documents, and the fix is a memo invalidated by
`writeIndex`.

## 3.6 — `flattenGlyphs` re-runs on every hydration of the same page — CODE

`preview.ts::fill` calls `flattenGlyphs(w.pages[i])` each time a page is drawn.
`evictIfCrowded` empties pages beyond `KEEP_PAGES`, so scrolling back and forth
across a long document re-flattens the same SVG repeatedly — two global regex
passes plus a rebuild of a multi-hundred-kilobyte string, in idle time, but
paid every time.

The result is a pure function of the page, and every page already has a stable
name: `w.hashes[i]`. A bounded `Map<hash, flattened>` removes the repeat
entirely.

# §4 — Missing, half-implemented, and behaving differently from what is written down

## 4.1 — Every pane-strip control is announced as its glyph — **CONFIRMED**

`main.ts`'s app-chrome header states the rule and the reason:

> *"a `title` tooltip is not an accessible name, so a screen reader announced the
> toolbar as '†, button', '⁑, button', '▤, button' — forty-two of them, page-wide,
> with zero `aria-label` … So `iconBtn` requires a name and sets `aria-label`
> from it."*

`paneHead()` does not use `iconBtn`. It builds every control with a bare
`el("button", { class: "pane-btn", title, onClick }, [glyph])`. The accessibility
tree of the running product, two panes open:

```
@e51 [button] "⇅"      @e52 [button] "◫"      @e53 [button] "⊟"
@e54 [button] "⋯"      @e56 [button] "⊡"
@e57 [button] "⇅"      @e58 [button] "◫"      @e59 [button] "⊟"
@e60 [button] "⋯"
```

Text content wins over `title` in accessible-name computation, so these are
named `"⊟"` and not "split down" — the exact failure the comment says was closed,
surviving one module over. Eleven controls, on every pane, in the surface a
writer uses to arrange their window. The same applies to the `+` in the font
picker and the floating preview button (13 in total on a default two-pane
window).

Note the strip's own comment anticipated something adjacent and stopped short:
*"Each control names itself. The strip is the one place in the application whose
buttons are pure glyph, so the only other thing that could identify them is the
`title`."* — which is a statement that they are *not* named, written as though it
were a fix.

**Fix.** Route `paneHead`'s buttons through `iconBtn`, which already takes the
name and sets both `title` and `aria-label`. The `data-pane-act` attributes the
acceptance script drives by are unaffected.

## 4.2 — `watch.forget` has no caller — **CONFIRMED**

```
$ grep -rn "watch.forget" --include=*.ts ksav/app/src
(no matches)
```

`watch.ts` exports it with the comment *"Forget a document — on close, or when
its binding is replaced."* Neither `closeOpenDoc`, `removeDoc`, `saveFileAs` nor
`openBound` calls it. The consequence is small (`known` retains one stamp per
document ever opened, keyed by an id that is never reused) but the comment is a
false statement about the program, and this repository's own findings register
treats that as the defect rather than the leak.

**Fix.** Either call it from `closeOpenDoc` and `removeDoc`, or delete it and the
comment. Per `build-dont-delete`, the first.

## 4.3 — Desktop file autosave silently never runs after a restart — CODE

Three correct pieces compose into a feature that does nothing:

1. `src-tauri/src/lib.rs::ksav_write_file` refuses any path not chosen in a
   dialog **this session** — deliberately, and the comment says so.
2. `files.ts::hasWritePermission` returns `true` for `kind === "tauri"`
   unconditionally. It has no way to ask (1) anything.
3. `save.ts::autosaveToFile` therefore proceeds, `files.saveTo` catches the
   rejection and returns `false`, and the caller returns `false` silently —
   *"a background save that fails must not steal the writer's attention; the
   next manual Save will report it properly."*

So on the desktop build, a document bound to a file from a previous session gets
no autosave at all, for the whole session, until the writer performs a manual
Save or Open. `markFileSaved()` is never reached, so the unsaved dot stays up —
which is honest, and is the only signal, and reads as "you have unsaved changes"
rather than "the thirty-second autosave you were promised is not running".

Ctrl+S handles this correctly (`written === false` routes to `saveFileAs`), which
is why it has not been noticed.

**Fix.** Give the shell a `ksav_path_allowed` command and have
`hasWritePermission` ask it, so `autosaveToFile` stands down for the honest
reason; or, better, have the desktop re-admit a recalled binding's path at boot
when the file still exists and the writer confirms once.

## 4.4 — A settings write that fails is silent, while a read that fails has a banner — CODE

`settings.ts::saveSettings` swallows the quota exception. `settingsLoadFailure()`
exists and `boot()` raises `showChromeNotice(tf("settingsLost", …))` for it — but
only for *load*.

Everything in one localStorage key: keybindings, macros, custom commands,
snippets, `savedArrangements` (whole pane trees), and `settings.tabs` (every
tab's serialised tree, rewritten by `rememberPanes()` on every splitter drag,
link toggle and document switch). localStorage is roughly five megabytes for the
whole origin, and it is shared with `ksav.library`, `ksav.recovery` (a full
document body) and `ksav.userWords`.

When it fills, every preference the writer sets from then on is accepted by the
UI, applied for the session, and gone on reload — which is
`no-preference-ever-survived-a-reload` reintroduced by a different route, with
the difference that the machinery to report it already exists and is wired to
the wrong half.

**Fix.** Give `saveSettings` a failure flag and raise the same banner. It is the
symmetric case and the string is already written.

## 4.5 — The paste handler drops every selection but the main one, and hides the paste from the macro recorder — **CONFIRMED (partial)**

`makeState`'s `EditorView.domEventHandlers.paste`:

```ts
const at = v.state.selection.main;
v.dispatch({
  changes: { from: at.from, to: at.to, insert: plain },
  selection: { anchor: at.from + plain.length },
});
```

Confirmed live that this handler is the one that runs on `ksav serve` (a
synthetic `ClipboardEvent` carrying `text/plain` inserted the marker text). It is
active on the server and desktop builds — everywhere `sourcesOf(backend)` is
non-null, which is every shipping build except the browser-only wasm one.

Two consequences:

* **Multi-cursor paste is silently lost.** CodeMirror's own paste inserts into
  every range; this replaces `selection.main` only. Every other range is left
  untouched with no indication.
* **A paste is invisible to the macro recorder.** The dispatch carries no
  `userEvent`, and the recorder's filter is
  `if (!tr.isUserEvent("input")) continue;`. The comment directly above that
  filter says the opposite: *"Read off the transaction rather than off keydown,
  so an IME, **a paste** and a nikud button all record as the text they
  produced."* A macro recorded with a paste in it replays without it.

**Fix.** `changes: v.state.changeByRange(r => ({ changes: {from: r.from, to: r.to, insert: plain}, range: ... }))`,
and add `userEvent: "input.paste"` to both this dispatch and the replacement one.

## 4.6 — `takeRefreshed` locates a citation with `indexOf`, so a repeated ref never updates — CODE

```ts
const at = doc.indexOf(row.ref);
```

A sefer that cites the same place twice — routine — has two occurrences of
`girsa:…`. `indexOf` finds the first, always. Accepting the refreshed text
rewrites the first citation; the second is never reachable, and the panel offers
the row again with the same button, which now edits the already-corrected first
one.

Also: `takeRefreshed` ends with `showRefreshed([row])`, which **replaces the
whole list** with the single row just accepted. A reader working down forty
refreshed citations loses the other thirty-nine the moment they accept one.

**Fix.** Collect every occurrence and disambiguate, or track a per-row offset
and search from it. For the panel, re-render the full list with the accepted row
marked, rather than replacing the list.

## 4.7 — Declining a handed-over document inserts it anyway — CODE

`takeArrivals`:

```ts
const hasText = runtime.view.state.doc.length > 0;
if (hasText && !(await ask(tf("documentArrived", arrival.display)))) {
  insertSnippet(arrival.markup);        // ← the "no" branch
  continue;
}
```

The prompt asks whether to replace what is open. Answering **no** splices the
whole handed-over document into the middle of the sefer at the caret. The
comment above it reads *"Never replaces what is open without being asked"*,
which is true and is not the whole promise a reader hears when they press No.

If inserting-at-caret is the intended third option it needs to be offered as
one — the modal has two buttons and three outcomes.

**Fix.** Either make No do nothing, or make it a three-way choice (replace /
insert here / discard). The second is more useful; either is better than a No
that edits the document.

## 4.8 — Removing an image never reclaims its blob — CODE

`collectAssets()` — the sweep that drops unreferenced blobs — is called from
exactly one place, `deleteDoc`. `removeAsset` takes the asset off the document
and calls `saveNow()`, which writes a document record with one fewer hash in it
and leaves the blob in the `ASSETS` store forever.

A writer who attaches a scan, changes their mind, attaches another, and repeats
accumulates every rejected 8 MB image in IndexedDB with nothing that will ever
free it. The store's own quota banner is what they eventually meet.

**Fix.** Call `collectAssets()` from `removeAsset` too. It is already written to
be safe to run at any time (it sweeps rather than reference-counts, exactly so
that this is true).

## 4.9 — Attaching a font marks nothing dirty — CODE

`insertImage` attaches and then inserts `#תמונה(…)`, which is a document edit and
therefore schedules a save and marks the bound file dirty. `addFont` attaches and
inserts **nothing** — the writer types the family name into the font box
themselves, which is documented and correct.

The consequence is that the font is written to the library copy (`attachAsset`
awaits `docs.putDoc`) and never to the bound `.ksav` on disk, because nothing
called `save.markFileDirty()`. Send that file to somebody and the font is not in
it, silently, with the document still referring to it by family name.

**Fix.** `save.markFileDirty()` at the end of `attachAsset`.

# §5 — Everything else

## 5.1 — `ksav in.ksav -o out/` creates a directory called `-o` — **CONFIRMED**

`engine/src/main.rs` treats `args[2]` as the output directory with no validation:

```rust
let out_dir: PathBuf = args.get(2).map(PathBuf::from)
    .unwrap_or_else(|| input.parent().unwrap_or(Path::new(".")).to_path_buf());
if let Err(e) = std::fs::create_dir_all(&out_dir) { ... }
```

There is no `-o` flag; `usage()` documents a bare positional. Somebody typed the
flag anyway, and the CLI made a directory named `-o`, wrote eleven pages of SVG
and two PDFs into it, ignored the real output directory in `args[3]`, and printed
a success line. The evidence is committed to this working tree:

```
$ ls ksav/engine/-o/
get.page-1.svg  get.pdf  probe.page-1.svg  probe.pdf  rawbody.page-1.svg  …
```

(It is the untracked directory `git status` reports.)

`args[3]` and beyond are also silently ignored, and `--help`/`--version` are
only recognised at `args[1]`.

**Fix.** Refuse an output argument beginning with `-` with the usage text and
exit 2 — the same treatment `plain()` gives a git argument for the same reason —
and refuse extra positionals rather than dropping them.

## 5.2 — Page-image writes fail silently under a success line — CODE

Same file:

```rust
for (i, svg) in result.pages_svg.iter().enumerate() {
    let svg_path = out_dir.join(format!("{stem}.page-{}.svg", i + 1));
    let _ = std::fs::write(&svg_path, svg);          // ← discarded
}
println!("✓ compiled {} → {} ({} page(s), …)", …);
```

The PDF write is checked and exits 1 on failure. The SVG writes are not. A full
disk, a read-only directory or a path too long produces `✓ compiled … (43
page(s))` with no SVGs on disk and exit code 0 — which is the class of small lie
the rest of this file's comments are proud of having removed.

**Fix.** Collect the failures and report them, and exit non-zero.

## 5.3 — `drain()` destroys the inbox before the editor has taken it — CODE

`engine/src/post.rs::drain` empties the in-memory list **and truncates the file**
in one step, before the answer has reached the client:

```rust
let taken = INBOX.lock().map(|mut inbox| std::mem::take(&mut *inbox)).unwrap_or_default();
if !taken.is_empty() { remember(&[]); }
taken
```

The client's `inbox()` swallows every failure by design (*"a build with no Girsa
half, or a server that went away, is a thing to stop asking about quietly"*). So
a response lost between the engine and the tab — a reload landing between the
POST and the parse, a wasm worker killed by the compile timeout mid-poll — takes
the sources with it, from memory and from disk, with Girsa already told
`{"taken":true}`.

The module's own standard is the one this misses: *"spec.md §10's stated target
is AirDrop, and AirDrop does not lose the file when you close the window."*

**Fix.** Two-phase it: hand the arrivals out, keep them in the file, and clear
them on an explicit acknowledgement from the client (or on the next poll that
reports the previous batch's ids). The `Arrival` shape has no id; adding one is
the prerequisite.

## 5.4 — The inbox file is rewritten in place — CODE

`post.rs::remember` uses `std::fs::write(&path, body)` directly. `ksav_dictionary_write`,
twenty lines of comment away in the Tauri shell, states the house rule:

> *"Beside and renamed over, like every other file this project rewrites in
> place: a machine that stops mid-write must cost the last word added, not the
> zman's worth of them."*

The inbox is the file that holds sources somebody has already been told arrived.

**Fix.** Write to `ksav-inbox.jsonl.writing` and rename.

## 5.5 — A second tab blocks an upgrade forever — CODE

`store.ts::open` handles `onblocked` on the *new* side by rejecting. Nothing
handles `db.onversionchange` on the *old* side, so an already-open connection
never closes itself. A writer with two Ksav tabs open, on the day the schema
version moves, gets a permanent "IndexedDB upgrade blocked by another tab"
rejection in the new tab, with no indication that the fix is to close the other
one.

`dbPromise.catch(() => { dbPromise = null; })` correctly makes it retryable, so
the state does clear — once the writer works out why.

**Fix.** `db.onversionchange = () => db.close();` in `onsuccess`, and a
user-facing sentence on the blocked path.

## 5.6 — `store.forEach` hangs its promise if the visitor throws — CODE

```ts
req.onsuccess = () => {
  const cursor = req.result;
  if (!cursor) return;
  visit(cursor.value as T, String(cursor.key));   // ← may throw
  cursor.continue();
};
```

A throw escapes into the IndexedDB event handler. `cursor.continue()` is never
called, so the transaction never completes and `oncomplete` never fires — the
returned promise neither resolves nor rejects. `rebuildIndex` and
`collectAssets` are the callers; `rebuildIndex` runs on the recovery path, on
boot, awaited by `docs.init`, which is awaited by `boot()`. A single malformed
record would hang boot with a blank page.

The visitors are simple today. The comment already warns about one hazard
(*"the callback must not await"*) and not this one.

**Fix.** `try { visit(...) } catch (e) { reject(e); transaction.abort(); return; }`.

## 5.7 — A poisoned cache mutex silently drops an image that carried its bytes — CODE

```rust
if let Some(h) = &hash {
    cache().lock().ok()?.put(h.clone(), Arc::new(bytes.clone()));
}
```

The `?` is on the *lock*, inside the branch where the request already carried the
decoded bytes. If the mutex is poisoned (a panic elsewhere while it was held),
this returns `None` — dropping an asset the engine is holding in its hand,
which surfaces as a missing image in the writer's sefer with no diagnostic.

**Fix.** Use the bytes regardless of whether they could be cached:
`if let Ok(mut c) = cache().lock() { c.put(...) }` and fall through to the
`Some(Asset { … })` either way.

# §6 — Notes and the apparatus: one assumption, four surfaces

`note-commands.ts` opens with a finding it is proud of, and it is worth quoting
in full because everything in this section is that finding, still open:

> *"Four modules kept their own copy of this list … `notes.ts` — the only one on
> the **write** path — listed neither, and had not since before the English
> wave. What that cost, in an English document: `notesIn` found no notes at all
> … `noteDepthAt` answered 0 inside a note … Nothing failed, nothing was logged,
> and 2,580 tests passed: every one of them asked the question in Hebrew."*

The list was centralised. What was not centralised is every *other* place a note
command is written as a Hebrew string literal, and there are four of them.

## 6.1 — In an English document, notes are not treated as notes — **CONFIRMED**

`insert.ts::plan` routes an insertion to the note path by asking
`notes.noteFor(snippet)`, and `noteFor` matches against the `NOTE_CHOICES`
literals — every one of which is Hebrew (`#הערה[|]`, `#הערה_ב[|]`,
`#הערתסיום[|]`) — plus one fallback regex that is Hebrew by construction:

```ts
if (nested && /^#הערה_[גדהוז]\[\|?\]$/.test(s)) { … }
```

That is fine for the toolbar's fixed buttons, which pass Hebrew literals and are
translated later by `applyChoice` — the comment there says so explicitly:
*"`plan` short-circuits to this branch **before** `insertionAt`, so a note is the
one insertion that never passed through the translation every other command
gets."*

But `tieredNoteAt` does not pass a Hebrew literal. It calls
`tierCommand(tier, docLang())`, which returns `fnote`, `tier2`, `tier3` … in an
English document — deliberately, and for a good reason its own doc comment
gives. Those strings then reach `noteFor`, which has never heard of them.

Probe against the built modules:

```
Hebrew document    tieredNoteAt -> #הערה[|]     noteFor -> card "footnote" layer 0
Hebrew document    tieredNoteAt -> #הערה_ב[|]   noteFor -> card "nested"   layer 1
English document   tieredNoteAt -> #fnote[|]    noteFor -> NULL  (not treated as a note)
English document   tieredNoteAt -> #tier2[|]    noteFor -> NULL  (not treated as a note)

Hebrew tier 2   -> plan.kind = note (card nested, so head/tail/defer honoured)
English tier 2  -> plan.kind = edit  (plain splice: no head line, deferNoteBodies ignored)
English tier 1  -> plan.kind = edit  (plain splice: no head line, deferNoteBodies ignored)
English tier 4  -> plan.kind = edit  (plain splice: no head line, deferNoteBodies ignored)
```

Every route that produces a tiered note is affected: the toolbar's `⁑`,
`Ctrl+Shift+N`, the Insert menu's tiered item, and the notes pane's "hang another
note off this one". In an English document all four become a plain splice, which
costs two things:

* **The `nested` card's `head` line is never written.** That line is
  `#הגדרות_הערות(מספור: ("א", "1"), הזחה: (0em, 1.4em))`, and the card's own
  comment says what it is for: *"the commentary lettered א,ב,ג and the he'aros on
  it numbered 1,2,3 and indented, **so a marker says which layer it belongs
  to**."* Without it, an English two-layer apparatus prints both layers with
  indistinguishable markers and no indent. The document compiles. The page looks
  finished. A reader cannot tell which block a marker points into — which is the
  same class of failure `apparatus.ts` calls *"the quietest failure in the
  product"*.
* **`settings.deferNoteBodies` is ignored.** That preference is §1.5 of the
  plan, and the entire argument for routing every surface through one producer
  is that it is honoured everywhere. In an English document, from these four
  doors, it is honoured nowhere.

**Fix.** `noteFor` should not string-match. `note-commands.ts` already exports
`TIER_FAMILY`, `BAND_FAMILY`, `PAGEBAND_FAMILY` and `DEFAULT_NOTE_KIND` — the
tables that exist precisely so a command's language stops being a property of a
literal. Match on the command *name* through those, the way `opensNoteBody`
does, and both languages fall out. Alternatively, have `tieredNoteAt` return the
Hebrew form and let `applyChoice`'s existing `translated()` call do the work —
smaller, but it leaves `noteFor` still unable to recognise an English note that
arrives from anywhere else.

## 6.2 — Convert-a-note offers Hebrew commands, and writes them into an English document — **CONFIRMED**

`main.ts::openNoteMenu` builds its conversion targets from the same Hebrew
literals:

```ts
const targets = NOTE_CHOICES.flatMap(markersOf)
  .map((s) => /^#([A-Za-z0-9֐-׿_]+)/u.exec(s ?? "")?.[1])
  .filter((c): c is string => !!c && c !== note.command)
```

Read off the running product, right-clicking a note:

```
["#הערתסיום","#הערת_גיליון","#הערת_ימין","#הערת_שמאל","#הערת_תוכן",
 "#הערת_מקור","#מדף_א","#מדף_ב","#הערה_זרם","#הערה_ב","#מדור_א","#מדור_ב"]
```

Twelve Hebrew commands, and `convertNote` writes `#${command}[${body}]`
verbatim with no `translated()` anywhere on the path. So in an English document
the menu's only offer is to rewrite `#fnote` as `#הערה` — the exact complaint
`applyChoice`'s comment says was fixed for insertion (*"note markers arrived in
Hebrew in an English document while `#bold` did not"*), reachable through the
menu instead.

The `c !== note.command` filter compounds it: it compares a Hebrew list against
an English `note.command`, so the note's **own** layout is not excluded either.
An English writer is offered "convert `#fnote` to `#הערה`", which changes the
language of their document and nothing else, presented as a layout change.

There is a trap in the obvious fix, and it is worth naming because it would
re-open a bug the comment beside it records: the scaffolding step is
`choiceForCommand(command)`, and that function *also* matches Hebrew names only —

```
הערה     -> footnote      fnote     -> null
הערתסיום -> endnote       endnote   -> null
מדור_א   -> two-bands     band1     -> null
```

— so translating `targets` without also fixing `choiceForCommand` would make
`choice` null, skip `scaffold`, and reproduce *"converting a footnote to an
endnote produced an endnote with no `#הערות_בסוף()`: the 'collected and never
printed' failure, performed by the product and then reported back to the writer
as a lint."*

**Fix.** Both together: derive `targets` in the document's language (the
`translated` helper `applyChoice` already uses), and make `choiceForCommand`
match through the family tables rather than the literals.

## 6.3 — The "collected and never rendered" lint repairs in Hebrew only — **CONFIRMED**

`apparatus.ts` detects bilingually — `RULES[].collectors` and `.dumps` both list
English aliases, and `BAND_FAMILY` supplies the whole family in both languages.
The **repair** does not: `fix` is a Hebrew literal, and the stream form hard-codes
the Hebrew argument name.

```ts
fix: "#הערות_בסוף()",
…
? p.fix.replace("()", `(זרם: "${p.stream}")`)
```

Probe:

```
Hebrew, #הערתסיום with no dump  -> the one-click fix writes: #הערות_בסוף()
English, #endnote with no dump  -> the one-click fix writes: #הערות_בסוף()
English, #band1 with no dump    -> the one-click fix writes: #הערות_מדורגות()
English, streamed endnote       -> the one-click fix writes: #הערות_בסוף(זרם: "sources")
```

The last line is the worst of the four: a Hebrew command, a Hebrew argument name
and an English stream name in one call, written into the writer's document by a
button labelled "render the notes".

This is the surface with the least excuse, because it is the one whose whole
purpose is to repair a document, and because `endnotes` / `endnotes_side` /
`banded_notes` are already sitting in the same `Rule` object being used for
detection.

**Fix.** Make `fix` a pair (or a function of the language) and pick with
`docLang`, as `tierCommand` does. The English aliases needed are already
enumerated three lines above.

## 6.4 — The note menu is dismissible only because of a class collision — **CONFIRMED**

`openNoteMenu` builds its menu with
`el("div", { class: "spell-menu note-menu" }, …)` and appends it straight to
`document.body`. It is not in `PANELS`, so `closeOnEscape`'s derived sweep does
not know about it, `closeOnOutsideClick` does not know about it, and
`mountPanel`'s "one popup at a time" rule was never invoked.

It is nevertheless dismissed correctly — Escape closes it, an outside click
closes it, and repeated right-clicks produce one menu rather than a pile. I
expected the opposite and checked:

```
right-click a note        -> .note-menu count = 1
press Escape              -> 0
click elsewhere           -> 0
right-click four more     -> 1
```

The reason is that `PANELS`' `spell-menu` entry declares
`selector: ".spell-menu:not(.mekoros)"`, and the note menu carries
`.spell-menu` for its styling. So it is swept as though it *were* the spell
menu.

That is working, and it is working for a reason nothing states. The selector's
own comment records one deliberate borrow (*"the citation list below borrows
`.spell-menu` for its styling, so this …"*) and not this one; `styles.css`
already gives `.note-menu` its own rules, so the day somebody drops the shared
class for the styling it no longer needs, the note menu stops answering Escape
and no test goes red — `panels.test.mjs` can only mutate surfaces that are in
the registry.

`openPaneMenu`, written later in the same file, does it properly:
`mountPanel("pane-menu", box, document.body)`.

**Fix.** Give the note menu a `PANELS` entry and mount it through `mountPanel`.
One row, and it stops depending on a class it only wears for CSS.

# What was checked and is sound

Recorded because a finding list without one is not an audit, and because
re-auditing these should not be free next time.

* **No DOM XSS through document content.** `ksav-lang.ts`'s prose-mode table
  widget is the only place document text becomes `innerHTML`. `renderInline`
  escapes per character and recurses through the scanner rather than
  re-matching; `colspan` comes from `parseInt` in `spans.ts`. The preview's
  `innerHTML` takes engine-produced SVG under a CSP with `script-src 'self'`.
* **The cross-origin half of the API is correct.** A foreign `Origin` is refused
  outright with 403, not merely denied the CORS header, and the state-changing
  services are POST. Verified.
* **The Tauri filesystem allow-list holds.** Writes, reads and stat are all
  gated on paths chosen in a dialog this session, normalised through
  `canonicalize`, with traversal covered by a test.
* **git argument handling is right for branches, revisions and paths.** No
  shell anywhere, `plain()` refuses option-shaped words, paths after `--`,
  `core.quotepath=false` with `-z` porcelain so Hebrew filenames survive. The
  gap is the URL only (§1.3).
* **The page cache cannot desynchronise.** The engine keeps no per-client page
  state and answers only against the list on the request; `PageStore.expand`
  returns `null` rather than a half-filled result and the caller re-asks for
  everything.
* **`checkableText` is genuinely offset-preserving**, including across surrogate
  pairs, so the incremental splice arithmetic in `runSpellCheck` is correct. Its
  cost is the problem (§3.1), not its answer.
* **`spans.scan` is memoised on the text**, so `apparatus.unrendered`'s four
  apparent full document scans per lint pass are one. I checked this expecting
  a hot-path finding and there is not one.
* **Detection of unrendered notes is correctly bilingual**, including the
  deferred spelling where the layout is named as a *value*
  (`#הערה_בשם("1", סוג: הערתסיום)`) and no call to it appears anywhere. Only the
  repair is monolingual (§6.3).
* **`save.ts`'s serialisation is sound.** `savePending` chains, errors are
  caught inside the chain so it cannot break, and the failure banner is
  idempotent.
* **The app boots clean.** No console messages, no failed requests, correct
  status line, badge and word count on the release binary under `ksav serve`.

# Suggested order

1. **§6.1** — the one that costs a writer their sefer's legibility without
   saying anything. Match `noteFor` through the family tables.
2. **§1.1** and **§1.3** — the two lines that close remote drive of git.
   `-c protocol.ext.allow=never` and a reach-gated token check.
3. **§2.1** — one clamp, and the browser build's priority queue stops silently
   switching itself off.
4. **§6.2** and **§6.3** — the other two doors that write Hebrew into an English
   document, fixed together with `choiceForCommand` so the scaffolding does not
   go quiet.
5. **§4.5**, **§4.7**, **§4.6** — three places the editor changes a document in a
   way the writer did not ask for.
6. **§1.2** — verify the asset hash on insert.
7. **§3.1**, **§3.2**, **§3.3** — the three that are measurable on a real sefer.
8. **§4.1** — route `paneHead` through `iconBtn`.
9. Everything else.

Fences worth having, because each of these would have been caught by one:

* **Run the whole note-path suite in both languages.** This is the important
  one. `note-commands.ts`'s header already diagnosed the disease — *"2,580 tests
  passed: every one of them asked the question in Hebrew"* — and the cure was
  applied to one list rather than to the suite. Every assertion about
  `noteFor`, `choiceForCommand`, `plan`, `openNoteMenu`'s targets and
  `addDump` should be parameterised over `he` and `en`, and §6.1–§6.3 all go red
  at once.
* A prohibition sweep for a **Hebrew command literal on a write path** — a
  `#`-prefixed Hebrew name in a string that is inserted rather than matched.
  `noteFor`'s regex, `RULES[].fix` and `openNoteMenu`'s `targets` are all
  instances, and the existing `prohibitions.test.mjs` is the right home.
* An assertion that `WasmBackend.foregroundPending` is never negative, driven
  through a forced `failAll`.
* A sweep asserting every `<button>` the shell renders has an accessible name
  that is not its own text content — the same shape as the existing
  `prohibitions.test.mjs` sweeps, extended past `iconBtn` to the DOM.
* An assertion that every floating surface appended to `document.body` is in
  `PANELS`, so a surface cannot be dismissible by accident (§6.4).
* A test that a `POST /git` with no `Origin` from a non-loopback peer is refused.
* An engine test that a hash-only asset whose bytes were never sent under a
  *verified* hash comes back in `missing_assets`.
